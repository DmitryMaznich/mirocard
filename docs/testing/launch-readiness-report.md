# Готовность к публичному открытию — отчёт

Спека: `docs/superpowers/specs/2026-09-25-public-launch-testing-design.md`

## Итог

**Вердикт: открывать можно после трёх действий. Два из них за владельцем, одно — небольшая правка кода.**

1. **Письма: решение владельца от 26.09 — остаёмся на бесплатном Resend и считаем письма.** В ветке `feat/email-budget-consent-google` (не слита и не задеплоена): суточный бюджет — не больше 90 писем и 80 регистраций по email за скользящие 24 часа (`EMAIL_DAILY_CAP`, `EMAIL_SIGNUP_CAP`). Когда бюджет исчерпан, регистрация по email закрывается до следующего дня (`503 signup_paused_email_budget`, экран «приходите завтра»), а в канал ошибок приходит «email signup paused: daily budget reached». Вход через Google писем не тратит, но работает, только если задан `GOOGLE_CLIENT_ID`.
   **Риск, который это оставляет:** сценарий запуска — «сотни человек за вечер», а по email зарегистрируются первые **~80 в сутки**. Остальным в пик поста скажут «приходите завтра», и часть из них не вернётся. Смягчить: до поста настроить вход через Google (`docs/google-sign-in-setup.md` в той ветке); публиковать пост, когда бюджет свежий (утром, а не после дня тестов); следить за счётчиком в вечер запуска.
2. **N2 — что будет на 8-й день.** Пробный доступ 7 дней, оплата выключена: через неделю после поста все колоды каталога закроются, а кнопка «Оплатить» отвечает английской ошибкой 503. Нужно решение владельца: длиннее пробный период, промокод в посте или включение оплаты.
3. **N10 — «Противоположности» не устанавливаются** (нет ZIP для версии из каталога). Собрать и закоммитить колоду.

**Сильно желательно до поста (дёшево и заметно для новичка):** N3 — замки на всех колодах каталога выглядят как «всё платное»; N9 — работа в локальном режиме молча пропадает после регистрации (или убрать кнопку с экрана входа); N1 — вариант «Instagram» в «Как узнали»; N7 — лимит 10 регистраций в час с одного IP.

**Можно после запуска:** N4 (второе устройство), N8 (асинхронный scrypt: нужен только при пиках от 5 регистраций в секунду), N5, N6 (тексты).

**Что выдержало проверку:** весь путь новичка на эмуляции Android и iPhone; неверный пароль, повторная регистрация, двойной клик, восстановление пароля; 300 регистраций в минуту без единой ошибки; сохранность прогресса при перезагрузке, офлайне, двух устройствах, очистке браузера и порче токена; 19 из 24 колод во всех режимах — без ошибок консоли, 5xx и белых экранов.

**Что не проверено:** настоящий Safari (Smart App Control блокирует WebKit на этой машине — покрывает `docs/testing/device-checklist.md`); поведение Railway под нагрузкой (замеры локальные); оплата (выключена); педагогическая правильность заданий; жесты (перетаскивание, рисование) и 4 колоды, которые обход не прошёл целиком (см. блок 2).

**Как повторить:** `npm run test:env` (прод-сборка на временной БД с заглушкой почты), затем `npm run test:e2e` (все сценарии), `npm run test:load`, `npm run test:microbench`. Памятка на вечер запуска: `docs/testing/launch-day-runbook.md`.

## Что проверено и прошло (блок 1a)

Эмуляция Android (Pixel 7) и iPhone 13, оба на системном Chrome (см. ограничения ниже):
- полный путь новичка: регистрация → «Отправить повторно» → письмо → «Email подтверждён!» → «Перейти в приложение» → добавить ученика → взять колоду «Глаголы» → режим → PIN (придумать + повторить) → занятие стартует → выход, очистка браузера → повторный вход;
- двойной клик «Создать аккаунт» — одно письмо;
- повторная регистрация того же email — понятное сообщение;
- логин до подтверждения — «Email не подтверждён. Проверьте почту или запросите новое письмо» + кнопка;
- забыл пароль → письмо → новый пароль → вход.

**Ограничение:** на этой машине Windows Smart App Control блокирует неподписанные браузеры Playwright (WebKit и свежий Chromium). Настройку безопасности не трогали, поэтому движок **Safari не проверялся автоматически** — только размеры/UA/touch iPhone на Chrome. Safari покрывается ручным чеклистом устройств.

## Сохранность прогресса (блок 3)

Все сценарии зелёные (Android-эмуляция, `tests/e2e/chaos.spec.mjs`). Прогресс проверялся по серверу (`/students`, `/account-topics`, `/sessions`) до и после:
- перезагрузка посреди занятия: состояние не изменилось, приложение вернуло человека **в то же занятие**;
- офлайн посреди занятия: белого экрана нет, после восстановления сети ничего не потеряно и не задвоено;
- два устройства одного аккаунта занимаются параллельно: ученик и колода не задвоились, ошибок нет;
- очищенный браузер → вход: ученик восстановлен с сервера;
- испорченный токен: белого экрана нет;
- обновление версии колоды при старой в кэше: тема открывается без ошибок;
- локальный режим («Без аккаунта»): приложение работает, но после регистрации данные теряются (N9);
- окончание пробного периода: см. N2.

## Замеры нагрузки (блок 1b)

Локально, прод-сборка (`node backend/server.mjs`, `SERVE_STATIC=1`), заглушка Resend. Каждый «новичок»: регистрация → подтверждение → bootstrap → каталог → взять колоду → скачать → sync ученика → записать занятие. Параллельно 5 «уже занимающихся» пользователей раз в секунду открывают bootstrap. Локальный CPU ≠ Railway: на Railway цифры могут быть хуже.

| Ступень (за 60 с) | Ошибки | Регистрация p50 / p95 / max, мс | Остальные эндпоинты p95, мс | Фоновые пользователи p95 / max, мс |
|---|---|---|---|---|
| 50 | 0 | 49 / 131 / 224 | ≤ 46 | 30 / 273 |
| 150 | 0 | 35 / 60 / 89 | ≤ 33 | 19 / 53 |
| 300 | 0 | 42 / **1046** / 1708 | ≤ 251 | 101 / **1640** |
| 150 за 30 с | 0 | 543 / **1343** / 1752 | — | — |

**Микробенчмарк:** `scryptSync` = 42,5 мс на вызов (p50), max 50 мс. 300 регистраций в минуту дают ≈ 12,7 с полностью заблокированного event loop (≈ 21 % времени). Бэкап SQLite: 17 мс на 1000 аккаунтов, 54 мс на 5000. **Не проблема** (R4 снят). Оценка снизу: в тестовой БД нет истории занятий.

**Выводы**
- **Ни одной ошибки** на всех ступенях. Письма уходят все (505 из 505 на ступени 300).
- Узкое место одно: синхронный `scryptSync` (R3). От 5 регистраций в секунду p95 регистрации переваливает за 1 с, а у тех, кто уже занимается, бывают паузы до 1,6 с. Для поста в Instagram это пиковый сценарий, не типичный: сотни за вечер — это единицы в минуту, там всё быстро.
- **N8 (Важно, дёшево, в таблице находок):** перевести `createPasswordHash`/`verifyPasswordHash` на асинхронный `crypto.scrypt` (тот же формат хеша, старые пароли продолжают работать). Хеширование уйдёт в пул потоков и перестанет останавливать остальных.
- **Лимит Resend (R1), смоделирован:** заглушка отвечает 429 после 100 писем → регистрация остаётся быстрой (p95 55 мс), но письма не уходят. После Task 1 каждый сбой пишется в лог как `email send failed (verification, status 429)` и уходит в канал ошибок. Без платного плана Resend люди после сотого письма за сутки не смогут войти.
- **Один IP (R5/N7):** из 15 регистраций подряд с одного адреса 5 получили 429.
- **R6:** весь прогон подменял `X-Forwarded-For` и тем самым обходил лимит по IP. Для нашего сценария это **мелочь**, но на Railway стоит проверить, какой элемент заголовка ставит их прокси: сейчас сервер доверяет первому, а его присылает клиент.
- Прогон «почта отказывает» сначала показал p95 20 с и обрывы соединений. Это **артефакт скрипта**: клиенты без письма одновременно опрашивали заглушку и забили локальные сокеты. Контрольный прогон «только регистрации» при отказе почты: p50 38 мс, 0 ошибок. Скрипт исправлен (ожидание письма ≤ 5 с).
