## Что проверено и прошло (блок 1a)

Эмуляция Android (Pixel 7) и iPhone 13, оба на системном Chrome (см. ограничения ниже):
- полный путь новичка: регистрация → «Отправить повторно» → письмо → «Email подтверждён!» → «Перейти в приложение» → добавить ученика → взять колоду «Глаголы» → режим → PIN (придумать + повторить) → занятие стартует → выход, очистка браузера → повторный вход;
- двойной клик «Создать аккаунт» — одно письмо;
- повторная регистрация того же email — понятное сообщение;
- логин до подтверждения — «Email не подтверждён. Проверьте почту или запросите новое письмо» + кнопка;
- забыл пароль → письмо → новый пароль → вход.

**Ограничение:** на этой машине Windows Smart App Control блокирует неподписанные браузеры Playwright (WebKit и свежий Chromium). Настройку безопасности не трогали, поэтому движок **Safari не проверялся автоматически** — только размеры/UA/touch iPhone на Chrome. Safari покрывается ручным чеклистом устройств.

## Замеры нагрузки (блок 1b)

Локально, прод-сборка (`node backend/server.mjs`, `SERVE_STATIC=1`), заглушка Resend. Каждый «новичок»: регистрация → подтверждение → bootstrap → каталог → взять колоду → скачать → sync ученика → записать занятие. Параллельно 5 «уже занимающихся» пользователей раз в секунду открывают bootstrap. Локальный CPU ≠ Railway: на Railway цифры могут быть хуже.

| Ступень (за 60 с) | Ошибки | Регистрация p50 / p95 / max, мс | Остальные эндпоинты p95, мс | Фоновые пользователи p95 / max, мс |
|---|---|---|---|---|
| 50 | 0 | 49 / 131 / 224 | ≤ 46 | 30 / 273 |
| 150 | 0 | 35 / 60 / 89 | ≤ 33 | 19 / 53 |
| 300 | 0 | 42 / **1046** / 1708 | ≤ 251 | 101 / **1640** |
| 150 за 30 с | 0 | 543 / **1343** / 1752 | — | — |

**Микробенчмарк:** `scryptSync` = 42,5 мс на вызов (p50), max 50 мс. 300 регистраций в минуту дают ≈ 12,7 с полностью заблокированного event loop (≈ 21 % времени). Бэкап SQLite: 17 мс на 1000 аккаунтов, 54 мс на 5000. **Не проблема** (R4 снят). Оценка снизу: в тестовой БД нет истории занятий.

**Выводы**
- **Ни одной ошибки** на всех ступенях. Письма уходят все (505 из 505 на ступени 300).
- Узкое место одно: синхронный `scryptSync` (R3). От 5 регистраций в секунду p95 регистрации переваливает за 1 с, а у тех, кто уже занимается, бывают паузы до 1,6 с. Для поста в Instagram это пиковый сценарий, не типичный: сотни за вечер — это единицы в минуту, там всё быстро.
- **N8 (Важно, дёшево):** перевести `createPasswordHash`/`verifyPasswordHash` на асинхронный `crypto.scrypt` (тот же формат хеша, старые пароли продолжают работать). Хеширование уйдёт в пул потоков и перестанет останавливать остальных.
- **Лимит Resend (R1), смоделирован:** заглушка отвечает 429 после 100 писем → регистрация остаётся быстрой (p95 55 мс), но письма не уходят. После Task 1 каждый сбой пишется в лог как `email send failed (verification, status 429)` и уходит в канал ошибок. Без платного плана Resend люди после сотого письма за сутки не смогут войти.
- **Один IP (R5/N7):** из 15 регистраций подряд с одного адреса 5 получили 429.
- **R6:** весь прогон подменял `X-Forwarded-For` и тем самым обходил лимит по IP. Для нашего сценария это **мелочь**, но на Railway стоит проверить, какой элемент заголовка ставит их прокси: сейчас сервер доверяет первому, а его присылает клиент.
- Прогон «почта отказывает» сначала показал p95 20 с и обрывы соединений. Это **артефакт скрипта**: клиенты без письма одновременно опрашивали заглушку и забили локальные сокеты. Контрольный прогон «только регистрации» при отказе почты: p50 38 мс, 0 ошибок. Скрипт исправлен (ожидание письма ≤ 5 с).
