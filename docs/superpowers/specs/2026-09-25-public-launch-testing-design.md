# Тестирование перед публичным открытием — дизайн

Дата: 2026-09-25. Статус: на ревью у владельца.

## 1. Цель и рамки

**Сценарий запуска (решено с владельцем):** приложение `app.mironium.com` открывается
бесплатно (или по промокоду) после промо в Instagram. Ожидание — десятки–сотни
пользователей, с возможным всплеском в первые часы после поста: сотни человек за вечер
регистрируются и впервые пробуют темы.

**Что нужно получить:**

1. Список реальных слабых мест, ранжированный по тому, насколько сильно они ударят по
   новичку в первый вечер, — с исправлениями для блокеров до запуска.
2. Повторяемый набор проверок, который остаётся в репо и запускается перед каждым крупным
   релизом одной командой.
3. Готовность к «дню X»: владелец видит, что что-то ломается, раньше, чем об этом напишут
   пользователи.

**Вне рамок (сознательно):**

- Оплата (Stripe/Lava, `CHECKOUT_ENABLED`) — на запуске выключена; sandbox-прогон по
  `docs/sandbox-e2e-checklist.md` — отдельный будущий этап.
- Нагрузка уровня тысяч пользователей и целенаправленные атаки — вторичны при
  выбранном сценарии; безопасность проверяем только в объёме «новичок не может случайно
  увидеть чужое / сломать своё».
- Staging-окружение на Railway — не создаём (стоит денег); всё гоняется локально на
  прод-сборке. Результаты нагрузки поэтому **относительные** (локальный CPU ≠ Railway) —
  это учтено в критериях (п. 4).

**Жёсткие правила прогона:** прод и прод-БД не трогаем; реальные письма не шлём (Resend
заменяется заглушкой); тестовые данные живут во временной папке и удаляются после.

## 2. Риски, найденные чтением кода (гипотезы до тестов)

| # | Риск | Где | Почему важно в первый вечер |
|---|------|-----|------------------------------|
| R1 | **Лимит бесплатного плана Resend** (~100 писем/сутки, ~2 запроса/с — сверить в дашборде) | `backend/lib/mailer.mjs` | Логин закрыт до подтверждения email (`email_not_verified`). Когда лимит кончится, новые люди физически не попадут внутрь. |
| R2 | **Ошибки отправки писем невидимы**: только `console.error`, не `reportError` | `server.mjs` → `sendEmailVerificationEmail(...).catch(console.error)` | Даже при настроенном алерте владелец не узнает, что письма перестали уходить. Пользователь видит «проверьте почту» и ждёт вечно. |
| R3 | **`scryptSync` блокирует event loop** на каждой регистрации/логине | `backend/lib/security.mjs` | При всплеске логинов тормозит весь сервер, включая тех, кто уже занимается. |
| R4 | **Ежечасный бэкап синхронный** (`backupSqlite` + `integrity_check`) в том же процессе | `scripts/railway-backup-loop.mjs` | Периодическое «подвисание» сервера, растущее вместе с БД. |
| R5 | Лимит 10 регистраций/час на IP | `server.mjs` `checkRegisterLimit` | Семьи за общим IP (CGNAT мобильного оператора, центр, где логопед регистрирует родителей) получат 429. |
| R6 | `getClientIp` берёт первый элемент `X-Forwarded-For` (клиент может подставить) | `backend/lib/http.mjs` | Для нашего сценария не блокер; фиксируем, чтобы проверить, как Railway формирует заголовок. |

## 3. Исправить до запуска (не зависит от тестов)

Это решения, а не гипотезы, — делаются первыми, тесты затем подтверждают исправление.

- **F1 (R1). Перейти на платный план Resend** (Pro) до публикации поста. Альтернатива
  «пускать без подтверждения email» меняет модель безопасности аккаунтов — не
  рекомендую под дедлайн. Действие владельца в дашборде Resend; я проверяю домен/лимиты
  после.
- **F2 (R2). Ошибки отправки писем → `reportError`** (все вызовы `send*Email(...).catch`),
  плюс событие `trackEvent("email_send_failed", { kind, status })`, чтобы сбой был виден
  в том же канале, что и остальные ошибки.
- **F3 (тестируемость). `RESEND_API_URL` из env** (по умолчанию
  `https://api.resend.com/emails`), чтобы в прогонах подставлять локальную заглушку.
  Поведение прода не меняется.
- **F4 (готовность). Проверить, что `ERROR_REPORTING_WEBHOOK_URL` задан на Railway** и
  реально доставляет сообщение владельцу (тестовая ошибка до запуска). Если не задан —
  подключить к существующему Telegram-боту/группе.

R3–R6 исправляются только если тесты покажут, что это реально бьёт (критерии в п. 4).

## 4. Блоки тестирования

Порядок = приоритет. Каждый блок выдаёт находки в общий отчёт (п. 6).

### Блок 1 — Первый вход новичка под всплеском (главный)

**1a. Путь одного новичка в браузере** (Playwright, эмуляция iPhone/WebKit и
Android/Chromium, мобильный viewport):
лендинг-ссылка → регистрация (обе роли: parent/specialist) → экран «проверьте почту» →
кнопка «отправить ещё раз» → переход по ссылке из письма (берётся из заглушки) →
логин → онбординг → первая тема → завершение занятия → выход и повторный вход.
Плюс негативные ветки, которые новичок реально сделает: повторная регистрация того же
email, логин до подтверждения, неверный пароль, «забыл пароль» (письмо → новый пароль →
вход), истёкшая/повторно использованная ссылка подтверждения, промокод.

**1b. Всплеск по API** (Node-скрипт без зависимостей, против той же локальной прод-сборки):
ступени 50 → 150 → 300 «новичков» за короткое окно; каждый: регистрация → подтверждение
(ссылка из заглушки) → логин → bootstrap/каталог → скачивание 1–2 ZIP колод → пара
sync-запросов с прогрессом. Параллельно — фоновые «уже занимающиеся» пользователи, у
которых меряем задержку (именно они страдают от R3/R4). Отдельный прогон — с заглушкой,
отвечающей 429 после N писем (симуляция R1), чтобы увидеть, что видит пользователь и
появляется ли сигнал (F2).

Меряем: p50/p95/max задержки по эндпоинтам, долю ошибок, лаг event loop (`/healthz` +
замер), RSS памяти процесса, сколько писем «ушло», размер БД. Прогон бэкапа во время
всплеска (R4).

**Критерии провала:** любая 5xx; ошибка у фонового пользователя; p95 любого
пользовательского эндпоинта > 1 с локально на ступени 300; письмо не отправлено без
сигнала; потерянный или задублированный аккаунт. Порог 1 с локально выбран с запасом,
т.к. Railway-контейнер, вероятно, медленнее локального CPU.

### Блок 2 — Обход всех тем и режимов

Автомат (Playwright) под свежим аккаунтом: для каждой темы каталога (28 колод) × каждого
режима — открыть параметры, запустить занятие, сделать несколько шагов (кликом по
первому доступному варианту / вводом), дойти до экрана результата или N шагов, выйти.
Режимы и параметры берутся из самого каталога/реестра тем, а не хардкодятся, чтобы
новые темы попадали в обход автоматически.

**Падение:** ошибка в консоли, необработанный reject, белый экран / error boundary,
зависание (нет изменений DOM N секунд после действия), ZIP колоды не загрузился или
упал на fallback, запрос 4xx/5xx. Скриншот и лог на каждое падение.

Ограничение (честно): автомат не проверяет **педагогическую правильность** заданий —
только что тема не ломается. Смысловые ошибки — зона блока 4.

### Блок 3 — Сохранность прогресса (хаос)

Сценарии, каждый — отдельный Playwright-тест:
перезагрузка посреди занятия; офлайн посреди занятия и возврат сети; закрытие вкладки
до отправки sync; два устройства одного аккаунта занимаются параллельно; вход на новом
устройстве; очищенное хранилище (IndexedDB/localStorage) при живой сессии сервера;
обновление версии приложения с закэшированными старыми ZIP колод; истёкший токен
посреди занятия. **Критерий:** прогресс не теряется и не дублируется, приложение не
застревает в сломанном состоянии.

### Блок 4 — Живые устройства (ручной чеклист)

Только то, что эмуляция честно не проверит: iOS Safari и PWA «на экран Домой»
(safe-area по правилу из CLAUDE.md), звук/TTS/озвучка, touch drag-and-drop, клавиатура на
полях регистрации, письмо подтверждения открывается из почтового приложения телефона
и приводит внутрь. Чеклист на ~15 минут, отдаётся тестерам в Telegram-группу; ответы
собираются в `feedback/inbox.jsonl` существующим ботом.

## 5. Готовность к «дню X»

- Канал ошибок (F4) проверен тестовой ошибкой.
- Короткий runbook «первый вечер»: что смотреть (Railway logs/metrics, канал ошибок,
  счётчик регистраций vs отправленных писем), признаки беды и что делать (например:
  письма не уходят → проверить Resend dashboard; сервер тормозит → смотреть метрики CPU).
- Ссылка на откат: `docs/commercial-launch-runbook.md` §11.

## 6. Что остаётся в репо и формат отчёта

```
tests/e2e/                 # Playwright: блоки 1a, 2, 3
  playwright.config.mjs    # проекты iphone (webkit) + android (chromium), headed по умолчанию
  fixtures/                # поднимает прод-сборку на временной БД + заглушку почты
scripts/load/              # блок 1b: Node-скрипт всплеска, без зависимостей
scripts/fake-resend.mjs    # заглушка Resend: хранит письма, отдаёт ссылки, умеет 429
docs/testing/device-checklist.md   # блок 4
docs/testing/launch-day-runbook.md # п. 5
docs/testing/launch-readiness-report.md  # отчёт прогона
```

Команды: `npm run test:e2e`, `npm run test:load`. Зависимость: `@playwright/test`
(devDependency) + браузеры chromium и webkit.

Прод-сборка для прогона: `npm run build` → `serve:prod` с `MIROCARD_DATA_DIR` во
временной папке, `RESEND_API_KEY` = фиктивный, `RESEND_API_URL` → заглушка,
`CHECKOUT_ENABLED` выключен.

**Отчёт:** таблица находок — симптом, как воспроизвести, кого бьёт в первый вечер,
серьёзность (Блокер / Важно / Мелочь), предлагаемое исправление, статус. Блокеры
исправляются до запуска с отдельным подтверждением владельца на каждый деплой (правило
версионирования из CLAUDE.md).

## 7. Порядок работ

1. F2, F3 (код) + F1, F4 (действия владельца, я проверяю).
2. Инфраструктура прогона: заглушка почты, фикстура прод-сборки, Playwright.
3. Блок 1 (1a, затем 1b) → первые находки владельцу сразу, не в конце.
4. Блок 2, блок 3.
5. Чеклист блока 4 → в группу тестеров.
6. Сводный отчёт + runbook дня X.
