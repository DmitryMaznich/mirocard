# Раздел «Инструкции» — дизайн

Дата: 2026-07-12

## Контекст

На главном экране приложения есть нижний таб-бар с двумя вкладками: «Занятие» и
«Планировщик» (`src/features/home/HomeScreen.jsx`). Добавляем третью — «Инструкции»:
визуальные пошаговые инструкции для ребёнка на разные жизненные ситуации (первая —
«Уборка на кухне»), плюс «Конструктор инструкций» для родителя/логопеда, позволяющий
создать свою инструкцию прямо в приложении.

Похожая механика уже существует у темы «Рецепты» (`reading_dad_texts`,
см. `docs/superpowers/specs/2026-07-08-recipe-architecture-simplification-design.md`):
пошаговый показ карточек через компонент `InstructionTask`
(`src/topics/renderers/reading/index.jsx`), встроенные txt-файлы
(`content/recipes/*.txt`), парсер `parseRecipeTxt.js`. Раздел «Инструкции» — не то же
самое: он не завязан на Планировщик/сессию, доступен как отдельная точка входа с
главного экрана, и должен поддерживать создание контента пользователем внутри
приложения (у рецептов авторинг — только через файлы/скрипты разработчика).

## Архитектура

Рассмотрены три подхода:

1. **Лёгкий автономный движок + `account_kv`** (выбран). Новый экран/компонент показа
   шагов не завязан на систему topics/session/task-engine рецептов. Пользовательские
   инструкции синхронизируются через уже существующий паттерн `account_kv` +
   `syncQueue` (как у Планировщика) — без изменений на backend.
2. Пропустить инструкции через существующий `follow_instruction`/`InstructionTask` и
   session-стейт-машину рецептов. Отклонён: этот движок специально скроен под контекст
   Планировщика (topic+mode+session), тащит нерелевантный багаж (порции, ингредиенты,
   чек-листы), и есть риск задеть стабильность рецептов ради фичи, которой это не
   нужно.
3. Как (1), но с отдельной SQL-таблицей `instructions` на backend (по образцу
   `students`). Отклонён для MVP: сущность `{title, steps: string[]}` полностью
   покрывается уже проверенным паттерном `account_kv` (Планировщик хранит так же
   устроенные данные), а отдельная таблица — заметно больше backend-работы без
   выигрыша на этом этапе. Миграция на таблицу в будущем локальна и не затронет UI.

## Модель данных

Общий тип для встроенных и пользовательских инструкций:

```ts
type Instruction = {
  id: string;
  title: string;
  emoji: string;
  steps: string[];   // MVP: только текст, без heading/checklist/warning/image
  builtin: boolean;
  updatedAt: number;
};
```

- **Встроенные**: JSON-файлы в `content/instructions/*.json` (например,
  `kitchen_cleaning.json`), собираются в статический список на этапе сборки через
  `import.meta.glob(..., {eager: true})` — по духу как `builtinRecipesTopic.js`, но без
  DSL-парсера txt (не нужен: шаги — только простой текст).
- **Пользовательские**: хранятся в `account_kv` под ключами `instruction:<uuid>`.
  Синхронизация — существующий `pushOp('kv.upsert', {key, value})` +
  `syncQueue` (`src/core/syncApi.js`). Подгрузка при бутстрапе — существующий
  `GET /account/kv?prefix=instruction:` (аналог `pullRecipeKvFromServer` у рецептов).
  Никаких изменений в backend-роутах/схеме БД не требуется.
- Удаление пользовательской инструкции — soft-delete: значение перезаписывается с
  флагом `{deleted: true}` (или отдельная kv-delete операция, если такая уже есть в
  `sync-processor.mjs` — уточняется на этапе реализации).

## Навигация и экраны

1. **Таб-бар** (`HomeTabs`): третья вкладка «Инструкции», иконка — список с галочками
   (list-checks), активна всегда (без featureFlag, как «Занятие»).
2. **`InstructionsHomeScreen`** — сетка карточек (эмодзи + название): встроенные
   инструкции первыми, затем пользовательские (помечены тегом «Моя», с иконкой
   редактирования), затем плитка «+ Создать свою» (пунктирная рамка, иконка замка —
   вход через admin-lock).
   - Клик по карточке → `InstructionRunner`.
   - Клик по иконке редактирования на своей карточке (за admin-lock) →
     `InstructionConstructorScreen` с предзаполненными данными.
3. **`InstructionRunner`** — прохождение шагов:
   - Один шаг на экране, крупный текст (без иллюстраций/фото в MVP).
   - Сегментированная прогресс-полоса вверху, по одной отметке на шаг; пройденные —
     заполнены, текущая — подсвечена, будущие — пустые.
   - Кнопки «Назад» / «Дальше» (первый шаг — без «Назад»).
   - Клавиатура: ArrowRight/Enter/Space — дальше, ArrowLeft/Backspace — назад, Escape —
     выход к сетке (тот же паттерн, что в `InstructionTask` у рецептов).
   - Без привязки к ученику/сессии и без наградной механики занятий — это не режим
     Занятия.
4. **Экран «Готово»** — после последнего шага: заголовок «Готово!», короткая
   поддерживающая фраза, кнопка возврата к сетке инструкций.
5. **`InstructionConstructorScreen`** — за admin-lock:
   - Поля: эмодзи (выбор из фиксированного небольшого набора), название (текст), список
     шагов (текстовое поле на шаг + добавить/удалить + реордер стрелками ↑↓ — drag-and-
     drop на touch ненадёжен, поэтому не в MVP).
   - Валидация перед сохранением: название не пустое, минимум один шаг с непустым
     текстом.
   - «Сохранить» — optimistic: сразу обновляет локальный список, затем
     `pushOp('kv.upsert', ...)`.
   - «Удалить» (только для уже существующей инструкции) — soft-delete, тоже optimistic.
   - Полный CRUD: создание, редактирование, удаление собственных инструкций.
     Встроенные инструкции не редактируются и не удаляются.

## Поток данных

- При старте/бутстрапе: встроенные инструкции — из бандла (всегда доступны, даже
  офлайн); пользовательские — из локального кэша (IndexedDB), обновляются при
  `GET /account/kv?prefix=instruction:` по существующей логике бутстрапа
  (`src/core/bootstrap.js`).
- Создание/редактирование/удаление — сразу в локальном сторе (источник правды для UI),
  затем уходит в `syncQueue` → `/api/sync`. Офлайн-создание переживает reload и
  досылается при восстановлении сети — эта механика уже работает для Планировщика,
  ничего нового не пишем.
- Конфликты между устройствами — существующий last-write-wins по `updatedAt` (как у kv
  в целом); поскольку инструкция редактируется предположительно одним родителем с
  одного устройства за раз, сложный merge полей не требуется.

## Обработка ошибок и краевые случаи

- Пустой список пользовательских инструкций — сетка показывает только встроенные +
  плитку «Создать свою», без спецсообщений.
- Сбой отправки на сервер при сохранении — тихий retry через существующую очередь;
  инструкция остаётся видна локально, UI не блокируется ожиданием сети.
- Неверный PIN admin-lock — обрабатывается существующим компонентом лока, нового кода
  не требуется.
- Попытка сохранить инструкцию без названия или без шагов — блокируется валидацией на
  форме конструктора (кнопка «Сохранить» неактивна/показывает inline-ошибку).
- iOS safe-area: как и для любого нового экрана с фиксированным хедером/футером
  (`InstructionRunner` — верхняя полоса прогресса и нижние кнопки; `Constructor` —
  нижняя панель «Сохранить/Удалить»), применяется правило из `CLAUDE.md`
  (`var(--app-safe-top/bottom)`).

## Вне рамок MVP (сознательно не делаем)

- Иллюстрации/фото на шагах (решено: только текст).
- Типы шагов heading/checklist/warning/image, группировка по фазам прогресс-бара.
- Трекинг прохождения инструкций по ученикам/статистика для логопеда.
- Публичный шеринг/каталог пользовательских инструкций между аккаунтами.
- Drag-and-drop реордер шагов в конструкторе (используем стрелки ↑↓).

## Мокап

Интерактивный HTML-мокап (4 экрана: сетка, прохождение, готово, конструктор),
выдержанный в существующей визуальной системе приложения (тёплый крем + бирюзовый
градиент, `DM Serif Display`/`Nunito`, паттерн `hub-card`), был согласован с
пользователем в ходе брейншторминга. Иконки/шрифты в мокапе — иллюстративные, кроме
эмодзи на карточках (осмысленный контент) и подтверждённой иконки таб-бара
(list-checks).
