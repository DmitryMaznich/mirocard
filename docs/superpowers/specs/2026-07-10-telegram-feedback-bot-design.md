# Telegram feedback bot — design

## Проблема

В Telegram-группе добровольных тестеров Mirocard2 накапливаются баг-репорты, скриншоты и
предложения вперемешку с обычной перепиской. Сейчас их приходится вручную выцарапывать из
истории чата, чтобы обсудить с Claude Code и превратить в задачи. Нужен способ отмечать
ценные сообщения прямо в Telegram и получать их сюда, в рабочий репозиторий, в виде backlog.

## Цель

- Отдельный Telegram-бот в группе тестеров, который **молча** слушает переписку.
- Владелец (я) ставит реакцию 📌 на сообщение, которое считает стоящим фидбэком (баг,
  предложение, скриншот с проблемой) — только владелец, не любой участник группы.
- Бот сохраняет помеченное сообщение (текст, автора, скриншот, ссылку) в backlog-файл.
- Backlog синхронизируется на локальную машину, где я работаю с Claude Code, и мы вместе
  разбираем его по очереди.

## Не цель (out of scope v1)

- Бот не отвечает в чате, не подтверждает получение текстом, не ведёт диалог с тестерами.
- Не собирает *все* сообщения группы в backlog — только помеченные реакцией.
- Не даёт тестерам самим помечать сообщения.
- Не пишет в общую БД `mirocard.db` — отдельный файловый backlog.
- Не использует Google Sheets.

## Архитектура

```
[Telegram-группа тестеров]
        │ все сообщения (privacy mode off)
        ▼
[MirocardFeedbackBot, runtime-хост 192.168.1.163]
        │ персистентный кэш сообщений (диск, retention ~30 дней)
        │
        │ событие message_reaction (📌, только owner_id)
        ▼
  находит сообщение в кэше → докачивает фото → пишет запись
        │
        ▼
  runtime-хост: feedback/inbox.jsonl + feedback/screenshots/*.jpg
        │
        │ scripts/fetch-feedback-backlog.py (SSH, по запросу)
        ▼
  локальная машина: feedback/inbox.jsonl + feedback/screenshots/
        │
        ▼
  разбор backlog вместе с Claude Code, status: new → done (только локально)
```

Два процесса, два места хранения:

1. **Бот на runtime-хосте** — сборщик. Отдельный от `MirocardBackend2` процесс, свой Telegram
   bot-токен, свой Windows Scheduled Task (`MirocardFeedbackBot`). Никак не завязан на основной
   backend Mirocard2 и не трогает `mirocard.db`.
2. **Локальный `feedback/inbox.jsonl`** — рабочий backlog, с которым имеет дело Claude Code.
   Синхронизация одностороняя (runtime-хост → локальная машина); статус обработки живёт только
   локально и не пишется обратно на бота.

## Почему не переиспользовать Kaplieva_bot

На runtime-инфраструктуре уже есть работающий Telegram-бот (`kaplieva_bot.py`, Synology),
обслуживающий образовательный центр Каплиевой (родители, публикация материалов). Технически
можно было бы добавить туда обработчик `message_reaction` для группы тестеров Mirocard2.
Решили не делать так:

- Один процесс на два несвязанных продукта — баг в новом коде фидбэк-бота мог бы уронить бота,
  которым реально пользуются родители центра Каплиевой.
- `kaplieva_bot.py` живёт на Synology; Mirocard2 CLAUDE.md прямо требует не разворачивать
  runtime Mirocard2 на Synology — храним рабочий процесс на runtime-хосте Mirocard2, не мешаем
  инфраструктуру двух разных клиентов.

Вместо этого — новый bot-токен и новый скрипт по образцу `kaplieva_bot.py` (те же библиотеки,
тот же SSH/env паттерн), но полностью независимый.

## Формат данных

### `feedback/inbox.jsonl` (одна JSON-запись на строку)

```json
{
  "id": "chat123_msg456",
  "captured_at": "2026-07-10T14:22:00+02:00",
  "message_date": "2026-07-10T14:20:11+02:00",
  "author": "Иван Тестов (@ivan_test)",
  "text": "При открытии карточки рецепта пропадает кнопка Назад",
  "photo": "screenshots/chat123_msg456.jpg",
  "telegram_link": "https://t.me/c/123.../456",
  "status": "new"
}
```

- `id` — `{chat_id}_{message_id}`, стабильный ключ для дедупликации при синхронизации.
- `photo` — относительный путь внутри `feedback/`, `null` если фото не было.
- `telegram_link` — прямая ссылка на сообщение в группе (переход в контекст переписки).
- `status` — бот всегда пишет `new`. Локально Claude Code переключает на `done` после разбора.
  Бот это поле никогда не читает и не перезаписывает.

### Кэш сообщений (только на runtime-хосте, не синхронизируется)

Персистентное (не только in-memory) хранилище последних сообщений группы — нужно, чтобы бот
мог сопоставить реакцию 📌 с содержимым сообщения даже после своего рестарта. Хранит `message_id`,
текст, автора, `photo file_id`, timestamp. Retention: около 30 дней, затем запись вычищается.

### `.gitignore`

`feedback/` целиком в `.gitignore` — рабочие данные (в т.ч. бинарные скриншоты и текучий
backlog), не исходники приложения, в git не коммитим.

## Компоненты

1. **`feedback-bot/mirocard_feedback_bot.py`** (новый, деплоится на runtime-хост)
   - `python-telegram-bot`, без Anthropic/PDF-специфики — только приём сообщений, обработка
     `message_reaction`, запись в JSONL и в кэш сообщений.
   - Реагирует только на реакции от `OWNER_ID` (Telegram user ID владельца), игнорирует реакции
     остальных участников.
   - Токен и `OWNER_ID` — в `.env` на runtime-хосте, не в репозитории.

2. **`scripts/fetch-feedback-backlog.py`** (новый, аналог `fetch-production-db-backup.py`)
   - По запросу подключается по SSH к runtime-хосту, скачивает новые записи `inbox.jsonl` и
     соответствующие новые скриншоты.
   - Мержит по `id`: локальные записи (и их `status`) не перезаписываются, добавляются только
     отсутствующие локально.

3. **Windows Scheduled Task `MirocardFeedbackBot`** на runtime-хосте — автозапуск бота при
   перезагрузке, независим от таска `MirocardBackend2`.

## Обработка ошибок

- Реакция 📌 на сообщение, которого нет в кэше (слишком старое или бот был выключен на момент
  его прихода) → бот ставит ⚠️ вместо ✅, ничего не пишет в backlog. По отсутствию ✅ видно, что
  сообщение не захвачено.
- Ошибка записи в JSONL или скачивания фото → запись в лог-файл на runtime-хосте (аналогично
  `MirocardBackend2`), реакция ✅ не ставится вовсе — сигнал повторить.
- Падение/перезапуск процесса бота → Scheduled Task перезапускает; персистентный кэш переживает
  рестарт, backlog на диске не теряется.

## Тестирование

- Тестовый прогон перед вводом в прод: отправить в группу тестовое сообщение и сообщение со
  скриншотом, поставить 📌 на оба, убедиться, что обе записи появились в `inbox.jsonl` на
  runtime-хосте, скриншот скачался, ✅ проставился.
- Проверить кейс "реакция после рестарта бота на сообщение, пришедшее до рестарта" — ожидаем ✅
  (кэш персистентный, должен пережить рестарт).
- Проверить кейс "реакция на сообщение старше retention-окна кэша" — ожидаем ⚠️.
- Проверить `fetch-feedback-backlog.py`: повторный запуск не должен дублировать уже
  синхронизированные записи и не должен затирать локально проставленный `status: done`.

## Открытые вопросы для этапа реализации

- Конкретное значение retention-окна кэша сообщений (ориентир — 30 дней).
- Как именно бот получает Telegram user ID владельца для фильтрации реакций (config vs discovery
  на `/start`).
- Имя нового бота в @BotFather.
