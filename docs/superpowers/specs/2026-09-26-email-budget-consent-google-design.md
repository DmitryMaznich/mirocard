# Бюджет писем, согласие на новости, вход через Google — дизайн

Дата: 2026-09-26. Статус: на ревью у владельца.
Связано: `docs/superpowers/specs/2026-09-25-public-launch-testing-design.md` (риск R1 — лимит Resend).

## 1. Решения владельца

- Resend остаётся на **бесплатном** плане. Вместо перехода на платный — считаем письма и
  при исчерпании «сегодня регистрации закончились, приходите завтра».
- Нужна будущая рассылка «что нового» всем зарегистрированным → **согласие на новости
  собираем уже сейчас**, до поста, чтобы база подписчиков копилась с первого дня.
- Вход через **Google** — делаем. **Apple** — отложен (платный аккаунт $99/год, сложности с
  «Скрыть e-mail»; для веб-приложения не обязателен).
- Сам движок рассылки (часть C) — **после поста**, отдельной спекой.

## 2. Состав

| Часть | Что | Зачем до поста |
|---|---|---|
| A | Суточный бюджет писем + пауза регистраций по почте | иначе после лимита Resend новые люди молча не попадают внутрь |
| B | Согласие на новости | иначе все, кто придёт с поста, выпадают из будущей рассылки |
| G | Вход через Google | не тратит письма (Google сам подтверждает email) и снимает трение регистрации |

## 3. Часть A — суточный бюджет писем

**Учёт.** Новая таблица `email_send_log(id, kind, sent_at)` — строка на каждое письмо,
**успешно** принятое Resend. Без адресата (не нужен для учёта, не храним лишнего).
Окно — **скользящие 24 часа** (не календарные сутки: не знаем точно, когда Resend
обнуляет счётчик). Строки старше 7 дней удаляются при записи.

**Пороги** (env, меняются в Railway без деплоя):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `EMAIL_DAILY_CAP` | 90 | жёсткий потолок всех писем за 24 ч |
| `EMAIL_SIGNUP_CAP` | 80 | после него закрывается регистрация **по почте** |

Зазор 80→90 зарезервирован для уже зарегистрированных: «отправить письмо повторно» и
«забыл пароль». Значения по умолчанию ниже лимита бесплатного Resend при любом из
известных вариантов (100 или 150/сутки) — владелец сверяет точный лимит в дашборде и
при желании поднимает.

**Где проверяется.** `mailer.mjs` получает `kind` у каждого письма и перед отправкой
спрашивает бюджет; при превышении `EMAIL_DAILY_CAP` бросает `EmailBudgetExceeded` (без
запроса к Resend). Отдельно `handleRegister` **до создания аккаунта** проверяет
`EMAIL_SIGNUP_CAP` → `503 { error: "signup_paused_email_budget" }`. Аккаунт без
отправленного письма не создаётся — иначе человек застрянет в «pending».

**Эндпоинт статуса.** `GET /api/auth/signup-status` → `{ emailSignupOpen: boolean,
google: { clientId } | null }`. Экран регистрации дёргает его при открытии.

**Что видит человек.**
- Экран регистрации, почта закрыта, Google включён: форма скрыта, текст «На сегодня
  регистрация по почте закончилась — мы маленький проект и отправляем ограниченное число
  писем в день. Войдите через Google прямо сейчас или приходите завтра.» + кнопка Google.
- То же без Google: «…Регистрация откроется снова завтра — приходите, пожалуйста!»
- «Отправить повторно» / «Забыли пароль» при исчерпании жёсткого потолка: «Сегодня мы
  уже отправили все письма, какие могли. Попробуйте завтра.» (сервер: `503
  email_budget_exhausted`).

**Сигнал владельцу.** В момент, когда за окно впервые достигнут `EMAIL_SIGNUP_CAP`, —
`reportError(new Error("email signup paused: daily budget reached"), { scope: "email_budget" })`
не чаще раза в 12 часов (флаг в памяти процесса; после рестарта может прийти повторно —
допустимо).

**Основа.** Ветка строится поверх коммита `092d9feb` из `launch-testing` (Task 1 плана
тестирования: `RESEND_API_URL`, `reportEmailFailure`) — он переносится cherry-pick'ом,
чтобы не править одни и те же строки двумя разными способами.

## 4. Часть B — согласие на новости

**Хранение.**
- `accounts`: `marketing_opt_in INTEGER NOT NULL DEFAULT 0`,
  `marketing_prompt_answered_at TEXT` (чтобы не спрашивать повторно).
- Журнал `marketing_consent_events(id, account_id, action 'grant'|'withdraw', text_version,
  source 'register'|'google_signup'|'settings'|'prompt', created_at)` — доказуемость
  согласия (кто, когда, на какой текст, где).
- Текст версионируется константой `MARKETING_CONSENT_VERSION = "2026-09-26"`. Текст
  показывает фронт, версию в журнал пишет бэк; при любой правке текста константа меняется
  в обоих местах в одном коммите.

**Текст галочки** (по умолчанию **не отмечена**, отдельно от согласия на обработку данных):

> Присылайте мне письма о новых темах и обновлениях Mironium — не чаще пары раз в месяц.
> Отписаться можно в любой момент.

**Где спрашиваем.**
1. Регистрация по почте — галочка под согласием на обработку данных.
2. Экран «ещё шаг» после первого входа через Google (часть G) — та же галочка.
3. Настройки → аккаунт — переключатель «Письма о новых темах», изменение пишется в журнал.
4. **Уже зарегистрированные** (у кого `marketing_prompt_answered_at` пуст): один раз
   ненавязчивая карточка на главной: «Присылать вам письма о новых темах? Не чаще пары раз
   в месяц.» [Да, присылать] [Нет, спасибо]. Любой ответ проставляет
   `marketing_prompt_answered_at`; закрытие крестиком — тоже «нет» (не донимаем).

**API.** `PATCH /api/account/marketing { optIn: boolean, source }` — меняет флаг, пишет
событие, проставляет `marketing_prompt_answered_at`. `serializeAccount` отдаёт
`marketingOptIn` и `marketingPromptAnswered`.

**Не входит в B (это C):** ссылка «отписаться» в письме, сами письма. Пока писем нет,
отписка через настройки достаточна.

**Юридически:** политику конфиденциальности (`landing/privacy*.html` и legal-страницы в
backend) нужно дополнить: вход через Google (какие данные получаем), рассылка новостей
(основание — согласие, как отозвать). Черновик правок готовлю я, публикация — после «да»
владельца. Это не юридическая консультация.

## 5. Часть G — вход через Google

**Поток — всегда через переход на страницу Google (redirect), без всплывающего окна.**
Всплывающее окно ненадёжно в iOS PWA «на экране Домой», а один путь проще, чем два.

1. Кнопка «Войти через Google» (Google Identity Services, `ux_mode: "redirect"`,
   `login_uri = https://app.mironium.com/api/auth/google/callback`) на экранах входа и
   регистрации. `clientId` берётся из `/api/auth/signup-status` → нет `GOOGLE_CLIENT_ID` —
   кнопки нет (безопасное выключение).
2. Google присылает `POST /api/auth/google/callback` (form-urlencoded: `credential`,
   `g_csrf_token`). Сервер:
   - сверяет `g_csrf_token` из тела с одноимённой cookie (защита Google от CSRF);
   - проверяет ID-токен: подпись RS256 по ключам Google (JWKS
     `https://www.googleapis.com/oauth2/v3/certs`, кэш по `Cache-Control`), `iss` ∈
     {`accounts.google.com`, `https://accounts.google.com`}, `aud = GOOGLE_CLIENT_ID`,
     `exp` в будущем, `email_verified = true`. Без внешних npm-зависимостей
     (`crypto.createPublicKey({ format: "jwk" })` + `crypto.verify`). URL JWKS
     переопределяется env `GOOGLE_JWKS_URL` — только для тестов.
3. Поиск аккаунта:
   - по `account_identities(provider='google', subject=sub)` → вход;
   - иначе по email: есть аккаунт → **привязать** Google к нему и войти (Google подтвердил
     владение адресом). Если аккаунт был `pending` (не подтвердил почту) — активировать;
   - иначе — новый человек, аккаунт **пока не создаётся** (см. 4).
4. Сервер создаёт **одноразовый код** (случайный, хранится хэш, TTL 5 минут, одно
   использование) и отвечает `303` на `/?google_code=<код>`. В коде лежит либо
   `account_id` (вход), либо данные Google для регистрации (`email, sub, given_name,
   family_name`) — для нового человека.
5. SPA при старте (как уже делает для `/verify-email?token=`) видит `google_code`, убирает
   его из адресной строки и шлёт `POST /api/auth/google/exchange { code }`:
   - вход → `{ account, settings, token }` → **тот же путь завершения входа**, что у
     пароля (вынести из `LoginScreen.jsx` в общую функцию `completeLogin`);
   - новый человек → `{ needsProfile: true, signupCode, email, firstName }` → экран
     **«Ещё один шаг»**: «Кто вы?», «Как узнали?», согласие на обработку данных
     (обязательно), галочка новостей (необязательно) → `POST /api/auth/google/complete-signup
     { signupCode, role, referralSource, consentPersonalData, marketingOptIn }` → аккаунт
     создаётся **сразу активным**, пробный доступ как у обычной регистрации, запись в
     `account_identities`, возвращается `{ account, settings, token }` → `completeLogin`.
     Аккаунт не создаётся до согласия на обработку данных — поэтому код, а не аккаунт.
6. Пароль у Google-аккаунта: `password_hash = ""` (колонка `NOT NULL`;
   `verifyPasswordHash` для пустого значения уже возвращает `false`). «Забыли пароль»
   позволяет такому человеку завести пароль — владение почтой подтверждается письмом.

**Новая таблица** `account_identities(provider, subject, account_id, email, created_at,
PRIMARY KEY(provider, subject))`, `one_time_codes(code_hash PRIMARY KEY, kind, payload,
expires_at, used_at)`.

**Письма:** вход и регистрация через Google писем не отправляют → бюджет A не тратят.
Поэтому при закрытой регистрации по почте Google остаётся открытым.

**Аналитика:** `trackEvent("registration_completed", { role, referralSource, method: "google" | "email" })`.

## 6. Действия владельца

1. **Google Cloud Console** (бесплатно, ~30 минут; пошаговая инструкция будет в
   `docs/google-sign-in-setup.md`): проект → OAuth consent screen (Mironium, email
   поддержки, ссылки на политику/условия, домен `mironium.com`, подтверждение домена в
   Search Console) → Credentials → OAuth client ID (Web): Authorized JavaScript origins
   `https://app.mironium.com`, `http://localhost:5174`; Authorized redirect URIs не нужны
   для этого потока. Скопировать Client ID.
2. Railway → `mirocard-backend` → Variables: `GOOGLE_CLIENT_ID=<id>` (не секрет).
3. Сверить точный суточный лимит в дашборде Resend; при желании поменять
   `EMAIL_DAILY_CAP` / `EMAIL_SIGNUP_CAP`.
4. Одобрить правки политики конфиденциальности.

## 7. Тестирование

- **Backend (`node:test`):** бюджет (пороги, зазор, окно 24 ч, запись только успешных
  отправок, 503 до создания аккаунта); согласие (журнал, флаг, prompt-answered); Google —
  на **своих** RSA-ключах, поднятом локально JWKS (`GOOGLE_JWKS_URL`): валидный токен,
  чужой `aud`, просроченный, `email_verified=false`, битая подпись, несовпадение CSRF,
  повторное использование кода, истёкший код, привязка к существующему email, активация
  `pending`, регистрация без согласия на данные → 400.
- **Frontend (vitest):** галочка новостей не отмечена по умолчанию и уходит в запрос;
  экран регистрации при закрытой почте; карточка вопроса на главной появляется один раз;
  экран «Ещё один шаг».
- **Живая проверка:** реальный вход через Google на `http://localhost:5174` (Google
  разрешает localhost) в браузере, затем после деплоя — на iPhone в режиме «на экране
  Домой» (пункт в `docs/testing/device-checklist.md`).
