# Спецификация: приём платежей (Stripe Managed Payments / Paddle + Lava Top)

**Дата:** 2026-09-13
**Статус:** согласовано для реализации
**Тема:** монетизация Mironium — подписка, два платёжных рельса, доступ к контенту

## 1. Решение и границы

Mironium продаётся по подписке (уже отражено на лендинге, `landing/index.html#pricing`):

| План | Цена | Заметка |
|---|---|---|
| Месяц | € 9,90 / мес | без обязательств |
| Полгода | € 49,90 / 6 мес | «Оптимальный выбор», € 8,32/мес |
| Год | € 89,90 / год | € 7,49/мес |

Подписка открывает **весь контент разом** — без разделения на уровни/темы. Ручной канал доступа `accounts.feature_flags` (уже существует, используется для бета-грантов вроде `lesson_plan`) остаётся отдельным от подписки и не меняется.

Платёж принимается по **двум независимым рельсам**, разделённым по стране выпуска карты, а не по языку/локали пользователя:

- **Основной рельс** — Stripe Managed Payments (публичный preview с февраля 2026, встроенный merchant-of-record у Stripe) или, если он на момент реализации недоступен/незрел для нового аккаунта под словенский s.p., **Paddle** как зрелая альтернатива с тем же MoR-эффектом. Обслуживает весь мир, кроме карт, выпущенных в России и Беларуси (эти карты физически не проходят по международным рельсам Visa/Mastercard с 2022 года — не вопрос политики провайдера, а техническое ограничение сети). MoR берёт на себя расчёт и уплату НДС по OSS за все страны ЕС — отдельно регистрироваться в OSS не требуется.
- **Узкий рельс** — **Lava Top**, используется только для оплаты картой/СБП, выпущенной в России (аналогично — Беларусь). Не предлагается как рельс «для русскоязычных» — это следствие того, где физически выпущена карта, а не язык интерфейса или гражданство плательщика.

### Входит в эту реализацию

- Таблицы `subscriptions` и `payment_events`.
- Backend-эндпоинт создания чек-аута и два вебхук-приёмника (по одному на рельс).
- Экран «Подписка» в приложении (выбор/подтверждение плана + способа оплаты), экран перехода к оплате, экран возврата (обработка → успех).
- Обновление лендинга: CTA с `?plan=`, ряд «Принимаем к оплате», ссылки на Условия/Политику возврата в футере.
- Проверка доступа к контенту через активную подписку (в дополнение к существующим `feature_flags`).

### Не входит в эту реализацию

- Сам текст «Условий использования» и «Политики возврата» — это отдельная юридическая задача, не инженерная; экран и футер только ссылаются на страницы, которые появятся отдельно.
- Регистрация аккаунтов у провайдеров и прохождение их проверки бизнеса (KYB) — действие пользователя вне кода.
- Подтверждение у словенского računovodja схемы декларирования дохода с рельса Lava Top — вне кода, но блокирует реальный запуск этого рельса.
- Вывод/репатриация денег с любого из рельсов — вне кода, процесс пользователя.
- Скидочные коды, апгрейд/даунгрейд плана, семейные/групповые подписки.

## 2. Почему два рельса, а не один

Рассматривался единый рельс на всё (см. обсуждение вариантов в переписке) — отклонён:

- **Только Lava Top на всё**: работает технически, но заводить через российский платёжный рельс выручку от европейских клиентов, которая затем попадает на счёт словенского s.p., — прямой AML/санкционный риск для банка s.p. (ЕС в 2026 году в фазе анти-обходных пакетов санкций против РФ, банк-эквайер несёт основную ответственность за скрининг платёжного потока).
- **Только EU-провайдер на всё**: не работает технически для карт, выпущенных в РФ/Беларуси — Stripe и подобные провайдеры физически не обрабатывают такие карты с 2022 года.
- **Российское юрлицо + ЮKassa вместо Lava Top**: ЮKassa намного дешевле, но не решает задачу — принимает только карты российской экосистемы (Мир/Visa-RU/Mastercard-RU + белорусский/узбекский/таджикский/армянский партнёрские схемы НСПК), то есть не покрывает Европу вообще. Кроме того, репатриация прибыли из российского ООО резиденту недружественной страны (Словения в списке РФ) требует усиленного валютного контроля/согласования правкомиссии — независимая и более тяжёлая проблема, чем экономия на комиссии.

Вывод: два рельса решают две разные, технически непересекающиеся задачи. Смешение только повышает риск.

## 3. Схема данных

```sql
CREATE TABLE subscriptions (
  id                   TEXT PRIMARY KEY,
  account_id           TEXT NOT NULL REFERENCES accounts(id),
  provider             TEXT NOT NULL,          -- 'stripe' | 'paddle' | 'lava_top'
  plan                 TEXT NOT NULL,          -- 'monthly' | 'half_year' | 'annual'
  status               TEXT NOT NULL,          -- 'active' | 'past_due' | 'cancelled' | 'expired' | 'refunded'
  currency             TEXT NOT NULL,
  amount_minor         INTEGER NOT NULL,
  external_contract_id TEXT UNIQUE,            -- id подписки/инвойса у провайдера
  current_period_end   TEXT NOT NULL,
  cancel_at_period_end INTEGER DEFAULT 0,
  created_at           TEXT NOT NULL,
  updated_at           TEXT NOT NULL
);

CREATE TABLE payment_events (
  id           TEXT PRIMARY KEY,
  account_id   TEXT REFERENCES accounts(id),
  provider     TEXT NOT NULL,
  event_type   TEXT NOT NULL,      -- payment.success, subscription.recurring.payment.success, refund.success, chargeback.initiated...
  external_id  TEXT NOT NULL,      -- id события/инвойса у провайдера — ключ идемпотентности
  payload_json TEXT NOT NULL,      -- сырой JSON вебхука, для аудита и разбора споров
  processed_at TEXT NOT NULL,
  UNIQUE(provider, event_type, external_id)
);
```

Один аккаунт = максимум одна активная запись в `subscriptions` (upsert по `account_id`). `payment_events` — неизменяемый журнал, не используется для чтения статуса напрямую.

## 4. Платёжный флоу

1. Лендинг: клик по карточке плана → `https://app.mironium.com/?plan=monthly|half_year|annual`.
2. Приложение: если не залогинен — обычный вход/регистрация, затем редирект на экран «Подписка» с планом из параметра.
3. Экран «Подписка»: план и способ оплаты предвыбраны (способ оплаты — «Картой» по умолчанию, «МИР / СБП» вторым вариантом). Пользователь может сменить план/способ. Нажатие «Оформить» → `POST /api/billing/checkout {plan, method}`.
4. Backend: по `method` выбирает рельс (`card` → Stripe Managed Payments/Paddle, `mir_sbp` → Lava Top), создаёт pending-запись, вызывает API провайдера, получает `checkoutUrl`.
5. Приложение показывает экран «Открываем страницу оплаты…» и открывает `checkoutUrl` во внешнем браузере (не iframe — 3D-Secure редиректы не проходят в iframe на iOS PWA).
6. Пользователь платит на стороне провайдера.
7. Провайдер шлёт вебхук на `/api/billing/webhook/{provider}` → backend проверяет подлинность запроса, сверяет свой `orderId`, апсертит `subscriptions`, пишет `payment_events`, бампает `sync_revision` аккаунта.
8. Пользователь возвращается в приложение → экран «Обрабатываем оплату…», короткий polling статуса аккаунта (~20 сек) → «Подписка активна».
9. Продление: `subscription.recurring.payment.success` двигает `current_period_end`; `failed` после ретраев провайдера → `subscription.cancelled` → `status='expired'`.

**Открытый риск, не решаемый на уровне архитектуры:** неясно, поддерживает ли Lava Top настоящее автопродление (recurring) для карт «Мир» так же, как для Stripe/PayPal-based карт — по документации recurring завязан на Stripe/PayPal под капотом. Перед реализацией автопродления на этом рельсе нужно подтвердить это в поддержке Lava Top или в песочнице; если не поддерживается — на этом рельсе продление будет ручным (напоминание + повторная оплата), а не автоматическим.

## 5. Доступ к контенту

`hasActiveEntitlement(account)` = активная запись в `subscriptions` (`status='active'` и `current_period_end` не истёк) **ИЛИ** соответствующий флаг в `accounts.feature_flags`. Второе условие не меняется этой реализацией.

## 6. UI

Экраны (макеты подтверждены, см. артефакты в переписке):

- **Подписка** — список из 3 планов (радио-выбор, предвыбор из `?plan=`), два способа оплаты, кнопка «Оформить», ссылки на Условия/Политику возврата.
- **Переход к оплате** — спиннер, пояснение «данные карты нам не передаются» (снимает тревогу перед внешним редиректом).
- **Возврат** — одно состояние на два кадра: «Обрабатываем оплату…» пока ждём вебхук, «Подписка активна!» после.

Визуальный регистр — как у экранов настроек аккаунта (`.screen-header`, тёплый фон, teal `#4a9b8f`), не палитра тематических карточек-тренажёров.

Лендинг (`landing/index.html`):
- Кнопки карточек плана получают `?plan=...` в `href`.
- Новый ряд «Принимаем к оплате» под карточками (иконки — обобщённые пиктограммы способа оплаты, не точные товарные знаки Visa/Mastercard/Мир).
- Футер получает два новых пункта: «Условия использования», «Политика возврата».

## 7. Безопасность

- Проверка подлинности вебхука до разбора тела запроса (у Lava Top — `X-Api-Key`/Basic Auth заголовок, у Stripe/Paddle — их штатная схема подписи запроса); секреты только в переменных окружения Railway.
- Идемпотентность по `UNIQUE(provider, event_type, external_id)` в `payment_events` — повторная доставка вебхука не продлевает подписку дважды.
- Данные карты никогда не проходят через backend Mironium — оплата целиком на хостинг-странице провайдера.
- `refund.success` / `chargeback.initiated` обязательны в обработке: снимают доступ (`status='refunded'`), не оставляют «фантомную» подписку.

## 8. Рельс Lava Top — изоляция и вывод

- Выплаты с Lava Top **не заводятся** на банковский счёт словенского s.p. — выводятся на отдельную карту/кошелёк, не связанные с бизнес-банкингом. Это единственная практическая мера, снимающая AML-риск для банка s.p. (банк просто не видит эти транзакции).
- Баланс на Lava Top не копится — регулярный вывод, без долгого хранения (у сервиса есть прецедент заморозки выплат в 2022 году).
- Доход с этого рельса всё равно входит в общемировой доход резидента Словении и подлежит декларированию — вопрос механизма декларирования (не через официальную бухгалтерию s.p.) отдельно подтверждается у računovodja до включения этого рельса в продакшене.

## 9. Что нужно подтвердить до реального запуска (не блокирует написание кода, блокирует продакшен с реальными деньгами)

1. Доступность Stripe Managed Payments для нового аккаунта под словенский s.p. на момент реализации; если недоступен — переключиться на Paddle без изменения архитектуры (просто другой `provider` в той же схеме).
2. Реальное поведение recurring-продления на Lava Top для карт «Мир» (см. раздел 4).
3. Юридический текст «Условий использования» и «Политики возврата».
4. Подтверждение у словенского računovodja: схема OSS для основного рельса и способ декларирования дохода с рельса Lava Top.
5. Прохождение KYB-проверки в обоих провайдерах под словенский s.p.
