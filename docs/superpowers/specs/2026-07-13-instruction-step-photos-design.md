# Фото на шагах инструкций — дизайн

Дата: 2026-07-13

## Контекст

В «Конструкторе инструкций» (`InstructionConstructorScreen.jsx`) родитель/логопед
создаёт шаги как обычный текст. Нужно добавить возможность прикрепить фото к
каждому шагу, с ограничением размера — либо жёстким лимитом в килобайтах, либо
(предпочтительно) автоматической оптимизацией в WebP.

Проверено: у рецептов («Готовим еду») **нет** аналогичного механизма
пользовательской загрузки фото — их фото (`text.image`, `step.image`) это
исключительно статичные ассеты, зашитые в ZIP темы на этапе сборки/импорта
(`content/recipes/media/*.webp`, парсятся из `[file.webp]` в `.txt` рецепта,
см. `src/topics/renderers/reading/parseRecipeTxt.js`). Между устройствами у
рецептов синкается только текст (`recipe_override_*` через `kv.upsert`), не
фото. Значит эта фича — новый механизм, а не переиспользование существующего.

В проекте уже есть два непохожих прецедента работы с фото:

1. **Фото ученика** (`StudentEditScreen.jsx`) — client-side resize через
   Canvas (`resizeToDataUrl`, `maxSize`, JPEG quality 0.85), хранится как
   base64 dataURL внутри JSON-записи студента, синкается отдельной операцией
   `student.photo.upsert`. На backend `extractAndStorePhoto(db, dataUrl)`
   (`backend/lib/account-repository.mjs:14`) декодирует dataURL, считает
   sha256-хэш, кладёт в таблицу `photos (hash, content_type, data,
   created_at)` (уже существует, `backend/lib/db.mjs:132`) и заменяет
   значение поля на короткую ссылку `/api/photos/<hash>`. Отдаётся публично
   через `GET /photos/:hash` (`backend/server.mjs:1092`), без авторизации,
   кэш на год (контент-адресуемо по хэшу).
2. **Фото в Планировщике** (`plannerPhotos.js`) — Blob через
   `topics.saveFile/getFile` в IndexedDB (object store `topics`,
   `src/core/db.js`), с `resizeToBlob(file, maxDim, quality)` через
   `createImageBitmap` + `OffscreenCanvas` + `convertToBlob('image/jpeg',
   quality)`. Хранится **только локально**, не синкается на сервер.

Пользователь подтвердил: фото шагов инструкций должны синхронизироваться
между устройствами (как текст). Значит подходит паттерн (1), не (2) — но
общий, не привязанный к студенту.

## Модель данных

`Instruction.steps` меняется с `string[]` на:

```ts
type InstructionStep = { text: string; photo: string | null };
```

для встроенных и пользовательских инструкций одинаково. Встроенные
(txt-источник) всегда получают `photo: null` — синтаксис фото в txt-формате
не добавляется в этой итерации (симметрично тому, что у рецептов картинки —
статика, а не то, что родитель прикрепляет через UI).

Меняются: `builtinInstructions.js` (обёртывает распарсенный текст в
`{text, photo: null}`), `instructionsApi.js` (add/update принимают шаги в
новой форме), `instructionValidation.js` (проверяет `step.text`, не сырую
строку), `InstructionRunnerScreen.jsx` (рендерит `step.text` +
опционально `step.photo`), `InstructionConstructorScreen.jsx` (поле
текста + фото-слот на каждый шаг).

## Backend

Новый эндпоинт **`POST /photos`** (аутентификация — существующий
`requireAuth`, тот же, что защищает `/account/*` роуты — используется
только чтобы отсечь анонимную загрузку, `account.id` в само хранение
фото не попадает, т.к. `extractAndStorePhoto` уже контент-адресуемая
и не привязана к аккаунту, как и существующий `GET /photos/:hash`):

- Тело: `{ dataUrl: "data:image/webp;base64,..." }`.
- Защитный потолок: если декодированный бинарник больше ~3 МБ — 413 (клиент
  всегда сжимает до долей мегабайта, это только страховка от багов/обхода
  клиента, не основной механизм ограничения размера).
- Переиспользует существующую `extractAndStorePhoto(db, dataUrl)` — новых
  таблиц/миграций не требуется, таблица `photos` уже под это готова.
- Ответ: `{ url: "/api/photos/<hash>" }`.

Отдача — уже существующий `GET /photos/:hash`, новый код не нужен.

Как и весь backend в этом проекте, эндпоинт не деплоится через
`npm run deploy:prod` (тот трогает только фронтенд) — нужен отдельный
ручной шаг деплоя backend (SFTP + рестарт scheduled task
`MirocardBackend2`), см. `DEPLOYMENT.md`.

## Клиентская оптимизация фото

Новый переиспользуемый хелпер (по образцу `resizeToBlob` из
`plannerPhotos.js`, но заточенный под этот кейс):

- `createImageBitmap(file, {imageOrientation: 'from-image'})` → contain-fit
  resize до максимум **640px** по длинной стороне → `OffscreenCanvas` →
  `convertToBlob('image/webp', 0.72)`.
- Если WebP-кодирование недоступно/падает (старый Safari) — fallback на
  `'image/jpeg', 0.72`.
- Если `createImageBitmap` не может декодировать файл (битый/неподдерживаемый
  формат) — ошибка наверх, UI показывает «Не удалось обработать фото», ничего
  не прикрепляется.
- Итоговый файл почти всегда 15-40 КБ при таких параметрах — специального
  ручного лимита с отказом пользователю не показываем, оптимизация делает это
  ненужным (как и предпочёл пользователь).

## UI — Конструктор

- У каждого шага рядом с текстовым полем — один круглый фото-слот:
  - Нет фото → кнопка «📷», по тапу открывает `<input type="file"
    accept="image/*">` без `capture` (ОС сама предлагает камеру или галерею —
    как у главного фото ученика в `StudentEditScreen`).
  - Есть фото → миниатюра с крестиком поверх для удаления; тап по миниатюре
    (не по кресту) — заменить.
- Поток при выборе файла: сразу локальный превью (object URL исходного файла,
  пока идёт сжатие), затем в фоне — сжатие в WebP → `POST /photos` →
  подстановка вернувшегося `url` в `steps[i].photo`.
- Пока хотя бы одно фото шага находится в процессе загрузки — кнопка
  «Сохранить» неактивна (чтобы не сохранить шаг со ссылкой на ещё
  не готовое фото).
- Сбой загрузки (сеть/5xx) — инлайн-ошибка на конкретном фото-слоте с кнопкой
  «Повторить»; не блокирует сохранение остального текста формы.

## UI — Runner

Если `step.photo` не `null` — рендерится `<img className="instruction-step-img
instruction-step-img--inline" src={step.photo} alt="" />` над/рядом с текстом
шага. Это уже существующий, стилизованный в `src/styles.css` класс,
используемый рецептами для точно такого же случая («картинка внутри шага») —
новых CSS-правил не требуется.

## Обработка ошибок и краевые случаи

- Битый/неподдерживаемый файл изображения → инлайн «Не удалось обработать
  фото», ничего не прикрепляется.
- Сбой сети при загрузке → инлайн «Повторить», не блокирует остальное.
- Офлайн — то же самое: загрузка фото требует живого запроса (в отличие от
  синка текста через `kv.upsert`/`syncQueue`, фото не ставится в офлайн-
  очередь, т.к. это отдельный POST с бинарным телом, а не маленькая kv-
  операция) — пользователь получает понятную ошибку, а не тихо «зависшую»
  ссылку.
- Удаление шага с фото не чистит запись в таблице `photos` на сервере —
  таблица дедуплицируется по хэшу содержимого, «осиротевшие» строки безвредны
  и это уже принятое в проекте поведение (то же самое происходит при замене
  фото ученика).

## Тестирование

- `instructionsApi.test.js`, `instructionValidation.test.js` — обновляются
  под новую форму шага `{text, photo}`.
- Новый backend-тест на `POST /photos` в `backend/tests/` — через
  `node --test` (backend использует нативный test runner Node, не vitest,
  запускается `cd backend && npm test`).
- Клиентский ресайзер/оптимизатор изображений юнит-тестами не покрывается —
  в проекте нет прецедента тестирования подобного canvas-кода (`resizeToBlob`
  в `plannerPhotos.js` тоже без тестов), и в vitest+jsdom это ненадёжно
  тестировать без реального декодирования изображений.

## Вне рамок этой итерации

- Синтаксис фото для встроенных (txt-источник) инструкций.
- Очистка «осиротевших» фото на backend при удалении/замене.
- Ограничение количества фото на инструкцию (ссылки — короткие строки, не
  раздувают синкаемый блок значимо).
