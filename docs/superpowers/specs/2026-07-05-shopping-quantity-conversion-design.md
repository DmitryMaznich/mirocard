# Конвертация количеств ингредиентов в покупные величины

## Проблема

Ингредиенты в `content/recipes/*.txt` записаны в единицах, удобных для готовки ребёнком («1 картошка», «0.5 стакана гречки», «2 ст.л масла»). Список покупок (Планировщик → Покупки) сейчас показывает эти же единицы без изменений — но по кулинарной единице невозможно понять, сколько и чего покупать в магазине («0.5 стакана гречки» не соответствует ничему на полке).

Цель: список покупок должен показывать округлённую до реально покупаемой величины количество («1 кг картошки», «1 пачка гречки» → в терминах этого дизайна «100 г» с шагом округления, см. ниже), не трогая сами файлы рецептов (там единицы остаются кулинарными — это отдельная, ранее согласованная задача).

## Область изменений

`src/features/planner/*` (код) и скилл `new-recipe` (процесс) — не трогают `content/recipes/*.txt`.

Одно точечное исключение: единица «горсть» (см. ниже) для целых ягод — это правка формата самого рецепта (не только его отражения в списке покупок), поэтому `breakfast_champion.txt` и `kompot.txt` меняются как часть этой работы. `content/shopping/shopping.txt` и `content/pantry.txt` не меняются вообще.

## Горсть — новая единица рецепта для целых ягод (2026-07-05)

Коллега пользователя предложил измерять целые ягоды (клубника/малина/ежевика, свежие или замороженные) горстями, а не стаканом/граммами — у ягод нет предсказуемого объёма/веса в стакане (неровная форма, воздух между ягодами), горсть не менее точна и при этом ближе к философии проекта: единица = конкретное физическое действие ребёнка (как стакан/ложка), а не абстрактная мера. Изменение принято и уже применено:
- `breakfast_champion.txt`: клубника `2|горсти`, малина `1|горсть`, ежевика `1|горсть` (было в граммах).
- `kompot.txt`: замороженные ягоды `2|горсти` (было `2|стакана`); заодно поправлена строка «взять 1 стакан ягод» → «взять ягоды» в шаге подготовки продуктов — количество в этом шаге нарушало уже существующее правило скилла «количества в продуктах — никогда».
- Единица задокументирована в скилле `new-recipe` (раздел «Количества и порции») и в памяти `feedback_recipe_ingredient_units`.
- Для списка покупок горсть требует того же типа записи в таблице конвертации, что и стакан — см. черновик ниже.

## Готовые напитки из каталога — проверка охвата

Проверено, есть ли среди 26 рецептов ингредиенты — готовые напитки из категории «Напитки» каталога (сок, морс, холодный чай, вода обычная/газированная), которым нужна была бы конвертация в бутылки/литры вместо штук. Результат: единственный такой ингредиент в рецептах — «вода газированная» (`lemonade.txt`, `1|шт`) — уже штучный (бутылка), конвертация не нужна. Ни сок, ни морс, ни готовый холодный чай ни в одном рецепте как ингредиент не встречаются (только `tea.txt` варит холодный чай сам, из чайных пакетиков). Действие не требуется сейчас; если в будущем рецепте появится готовый бутилированный напиток как ингредиент — по аналогии с «вода газированная» оставлять в `шт` (бутылка/пачка уже покупная единица), запись в таблицу конвертации не нужна.

## Архитектура

Текущий пайплайн: `shoppingListGenerator.generateShoppingList` (суммирует qty по всем рецептам плана, ключ — `product.toLowerCase()`) → `plannerShoppingUtils.buildPlannerShoppingData` / `syncDecisionsIntoShoppingData` (резолвит продукт в товар каталога через `findFuzzyMatch`, форматирует `note` как `` `${qty} ${unit}` ``).

Добавляются два шва в этом же пайплайне, без смены общей структуры:

1. **Агрегация в граммах/мл** (`generateShoppingList`): каждый ингредиент конвертируется в канонический базис (граммы для твёрдого/сыпучего, мл для жидкого) до суммирования, а не после. Это заодно устраняет скрытый баг: если один продукт встречается в двух рецептах в разных единицах рецепта, сегодняшний код складывает сырые числа `qty` не приводя единицы — с конвертацией в граммы сумма становится корректной независимо от того, в каких единицах он был записан в каждом рецепте.
2. **Округление при показе** (`buildPlannerShoppingData`, `syncDecisionsIntoShoppingData`): вместо форматирования сырого `qty unit`, вызывается конвертер, который округляет граммы/мл вверх до шага покупки, характерного для продукта, и форматирует итог (`г`/`кг` или `мл`/`л` — автопереключение по величине).

Если продукта нет в таблице конвертации — оба шва падают на текущее поведение (сырые qty/unit из рецепта, без изменений). Ничего не блокируется и не крашится на неизвестном продукте.

## Модель данных

Новый модуль `src/features/planner/shoppingUnitConversions.js`, константа `SHOPPING_UNIT_CONVERSIONS`, ключ — нормализованное (lowercase) название продукта, совпадающее с ключом агрегации в `shoppingListGenerator.js`:

```js
export const SHOPPING_UNIT_CONVERSIONS = {
  'картошка': { gramsPerUnit: { 'шт': 150 }, roundStepG: 500, minG: 500 },
  'гречка':   { gramsPerUnit: { 'стакан': 210 }, roundStepG: 100, minG: 100 },
  'масло растительное': { gramsPerUnit: { 'ст.л': 15 }, roundStepG: 250, minG: 250, buyUnit: 'мл' },
  'творог':   { roundStepG: 200, minG: 200 }, // уже в граммах в рецепте — gramsPerUnit не нужен
  // ...
};
```

Поля одной записи:
- `gramsPerUnit` (опционально) — объект `{ [единица_рецепта]: граммы_или_мл }`. Нужен только продуктам, у которых единица рецепта — не граммы/мл (стакан/ст.л/ч.л/шт-по-весу). Продукты, уже указанные в `гр`/`мл` в рецепте, это поле не имеют — используется значение как есть.
- `roundStepG` — шаг округления вверх, в граммах (или мл, если `buyUnit: 'мл'`).
- `minG` — минимальная покупаемая величина (обычно равна `roundStepG`).
- `buyUnit` (опционально) — `'мл'` для явно жидких продуктов; по умолчанию граммы/килограммы с автопереключением (`< 1000` → `г`, иначе `кг`, аналогично для `мл`/`л`).

Функция `toShoppingQuantity(product, totalQty, unit)` в том же модуле:
1. Ищет запись по `product.toLowerCase()`. Нет записи → возвращает `{ qty: totalQty, unit }` без изменений.
2. Есть запись → если есть `gramsPerUnit[unit]`, конвертирует `totalQty` в граммы/мл; если единицы рецепта уже граммы/мл — использует `totalQty` как есть.
3. Округляет вверх до `roundStepG` (`Math.ceil(grams / roundStepG) * roundStepG`), применяет `minG` как нижнюю границу.
4. Форматирует: `< 1000` → `${grams} г` / `${ml} мл`; `>= 1000` → `${grams/1000} кг` / `${ml/1000} л` (до одного знака после запятой).

## Универсальное правило для «шт» без записи в таблице

Сейчас `note` форматируется как `Math.round(qty * 10) / 10` — округление до десятых, а не до целого. Это значит «0.5 шт лимона» так и останется «0.5 шт» — купить половину лимона нельзя. Добавляется отдельное, не зависящее от таблицы конвертации правило форматирования: **если итоговая единица — `шт`, всегда округлять вверх до целого числа** (`Math.ceil`), а не до десятых. Это правило применяется всегда, в том числе к продуктам без записи в `SHOPPING_UNIT_CONVERSIONS`.

## Продукты без записи в таблице (сознательно)

Единица рецепта уже равна покупной, дополнительная конвертация в граммы не нужна (действует только универсальное округление «шт» выше):
- штучные готовые к покупке товары: яйца, лимон, апельсины, огурцы, помидоры, перец болгарский, авокадо, редис, равиоли, багет, вода газированная, томатный соус, чай, йогурт обычный;
- зелень пучками (укроп, петрушка, базилик, мята, тимьян, зелёный лук) и чеснок зубчиками — уже ровно то, как это продаётся;
- «по вкусу»/кладовые продукты с пустым количеством (соль, специи, мука и т.п.) — количества нет, конвертировать нечего.

## Интеграция в скилл `new-recipe`

Новый шаг в разделе «Каталог продуктов» / чек-листе «Процесс адаптации»: если у ингредиента единица рецепта — стакан/ст.л/ч.л, либо шт для взвешиваемого товара (овощ, куриная часть), нужно добавить запись в `shoppingUnitConversions.js` (коэффициент + шаг округления). Если продукт уже есть в таблице — не трогать. Правило то же, что и для каталога товаров: **только добавлять, никогда не удалять/переименовывать существующие записи.**

## Тестирование

- Юнит-тесты `toShoppingQuantity`: конвертация с `gramsPerUnit`, продукт уже в граммах без коэффициента, округление вверх на границе шага, отсутствие записи → passthrough.
- Юнит-тест на универсальное округление «шт» вверх (0.5 шт → 1 шт) независимо от наличия записи в таблице.
- Юнит-тест `generateShoppingList`: один продукт в двух рецептах с разными единицами рецепта суммируется корректно в граммах.
- Ручная проверка на экране Покупки: сформировать план с 2-3 рецептами, содержащими картошку/гречку/масло, убедиться, что note показывает покупную величину, а не сырые кулинарные единицы.

## Что осталось нерешённым / низкий приоритет

- Чеснок в рецептах считается зубчиками; в некоторых магазинах чеснок продаётся головками, а не поштучными зубчиками — конвертация «зубчики → головки» не входит в эту итерацию, можно добавить отдельным пунктом в таблицу позже при необходимости.
- Значения `gramsPerUnit`/`roundStepG` в черновике — ориентировочные бытовые оценки, не результат замера; корректировка не требует изменения архитектуры, только правки данных в `shoppingUnitConversions.js`.
