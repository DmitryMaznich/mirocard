# Предлагаемый языковой контракт v1

Статус: технический проект целевой системы. [LOC-01](loc-01-prototype.md) реализует только локальный выбор RU/SL и ограниченный UI-прототип. Синхронизация аккаунта, учебный контекст, миграции и контракт пакетов ниже ещё не реализованы. Основание — [аудит](README.md). Изменения входят отдельными проверяемыми задачами; существующие идентификаторы тем, права доступа и данные не переименовываются ради перевода.

## 1. Язык и принадлежность настройки

| Значение | Хранение / смысл |
| --- | --- |
| `settings.uiLanguage` | Предпочтение аккаунта для взрослого интерфейса: `ru`, `sl`, впоследствии `en` |
| Локальная копия UI-языка устройства | Доступна синхронно до React/IndexedDB; остаётся после logout. Это boot-копия и гостевой выбор, не второй независимый язык аккаунта |
| `settings.cardLanguage` | Существующее API-поле общего предпочтения занятий; в UI называется «Язык занятий». Не делать немедленный breaking rename |
| `student.preferredLessonLanguage` | Новое отдельное предпочтение занятий ученика; nullable = наследовать. `primaryLanguage` сохраняет нынешний смысл |
| `session.contentLanguage` | Фактически выбранный язык материала, фиксируется при старте |
| `session.contentVersion`, `packageId` | Версия конкретного языкового материала и установленный артефакт; `topicVersion` сохраняется для старых путей |
| `material.language` | Язык авторского текста/записи; null = не установлен. Не вычисляется по UI-языку |

Внутренние коды языка — BCP 47 `ru/sl/en`; теги TTS/форматирования — отдельная явная таблица `ru-RU/sl-SI/en-…`. Английский регион выбрать после проверки содержания; язык не задаёт автоматически валюту, часовой пояс, праздники или страну. Названия в выборе: Русский, Slovenščina, English; флаги не используются.

Новый запуск разрешает язык в таком порядке: явный выбор подготовки → preferredLessonLanguage ученика → cardLanguage аккаунта → выбор взрослым из доступных языков режима. Если предпочтение недоступно, показать выбор/ограничение; не запускать русский материал молча. UI-язык может предложить первоначальный вариант, но не отменяет сохранённое предпочтение. Временный выбор относится к подготовке данного занятия и сбрасывается при смене ученика.

Старый русский пользователь после обновления видит прежнее поведение. Пока языковой контракт материала не введён, старый сценарий запуска остаётся legacy-путём; его нельзя одновременно рекламировать как словенскую версию.

## 2. Переводы взрослого интерфейса

Целевое решение: `i18next` + `react-i18next`, JSON namespaces `common/auth/students/library/session/settings/history`, ICU-подобное склеивание фрагментов не вводить. В LOC-01 пока используется ограниченный модуль без новых зависимостей для простых сообщений; он не реализует plural API и не предназначен для перевода учебных фраз. Перед расширением на количественные сообщения подключить i18next с `Intl.PluralRules`; даты, числа и длительности — централизованные formatter-функции `Intl` с явным locale. До добавления зависимостей проверить bundle и работу браузеров из проекта.

Ключ отражает смысл (`auth.login.invalidCredentials`), а не русский текст. Переменные именованные, фраза переводится целиком. Для словенского обязательны используемые категории `one/two/few/other`; тестовые количества 0, 1, 2, 3, 4, 5, 11, 12, 101, 102. Не копировать русский алгоритм последних цифр. Для согласования существительного/прилагательного числа недостаточно: учебные формы проверяются в языковом модуле.

Ссылки и выделение оформляются React-компонентами (например, Trans); не вставлять HTML из непроверенного словаря. Текст пользователя не становится ключом перевода.

Разрешённый runtime fallback взрослого интерфейса — RU с диагностикой отсутствующего ключа; опубликованный SL-сценарий до выпуска обязан пройти проверку полноты обязательных ключей. При отсутствии английского namespace английский не предлагать как готовый UI. Метаданные каталога могут иметь отдельный fallback с видимой пометкой; он ничего не говорит о языке задания.

## 3. Старт и синхронизация предпочтений

1. Минимальный bootstrap до React читает только проверенный код локального UI-языка, устанавливает `document.documentElement.lang` и язык статического сообщения загрузки. CSS/шрифт не должен зависеть от ответа сервера.
2. Ручной выбор сначала сохраняется локально, затем меняет UI без перемонтирования экрана и сброса формы. При авторизованном выборе создаётся долговечная pending-операция только языковой настройки.
3. Поздний bootstrap не перезаписывает неотправленный ручной выбор. После подтверждения операции серверное значение становится основанием для следующих входов. Смена языка на другом устройстве применяется после подтверждённого pull, сохраняя текущее занятие.
4. Поля предпочтений получают серверную ревизию либо сравнение с ожидаемой ревизией; не полагаться на точность часов устройства. Изменение uiLanguage не отправляет весь settings и не перетирает PIN/другие настройки.
5. В существующем `processSync` нет settings-операции: добавить обработчик либо отдельную долговечную очередь PATCH с повтором и идемпотентностью. Простого `.catch(() => {})` недостаточно.
6. Для гостевого выбора и старого серверного default `ru` нужен признак «выбрано явно». Предложение: nullable `ui_language_revision/selected_at` с серверным временем; новое пустое предпочтение принимает гостевой выбор, существующее явное — сохраняется. Семантику проверить на старых аккаунтах без массовой смены языка.
7. Logout удаляет данные аккаунта как раньше, но сохраняет boot-копию языка; авторский материал не остаётся в новой гостевой сессии из-за языковой настройки.

Конкретные миграционные поля фиксируются в LOC-02 после прототипа; этот раздел задаёт инварианты и сценарии конфликта, а не готовую SQL-миграцию.

## 4. Контракт engine/renderer

```ts
type LanguageContext = {
  contractVersion: 1;
  uiLanguage: 'ru' | 'sl' | 'en';
  contentLanguage: 'ru' | 'sl' | 'en';
  topicId: string;
  packageId: string;
  contentVersion: string;
};
```

Генератор получает LanguageContext, локализованный набор карточек и языковой модуль до построения tasks. Renderer получает тот же зафиксированный контекст и функции `tUi`, `tLesson`, форматирования и аудио через явные props. Импорт глобального app i18next в учебный engine не допускается: смена UI не меняет очередь или озвучку. Хост передаёт функции, а не экземпляр библиотеки переводов внутрь ZIP.

Новый manifest объявляет `languageContractVersion`, `contentLanguage`, `contentVersion`, `packageId`, доступные mode IDs и необходимые ресурсы. Пример идентичности пакета — `comparison:sl:<contentVersion>`; лицензия и каталог продолжают использовать `comparison`. Способ общего хранения изображений проверить прототипом, не включать в пилот обязательную загрузку всех языков.

`deriveConcepts` больше не выбирает русский заранее. Подпись и аудио выбираются из содержания конкретного языка; отсутствие обязательного ресурса возвращает структурированную причину до старта. Старый renderer без версии контракта работает в legacy-пути и не объявляется SL-совместимым. Проверить как bundled fallback, так и реальный загруженный ZIP, включая исключение spatial_prepositions.

## 5. Пакеты, кэши и установка

Файлы, record метаданных, кэш renderer, DOM-id CSS и audioOverrides получают полную идентичность packageId/языковой версии; одного изменения `topicKey` недостаточно. Перечень installedTopicIds, update/remove/list, builtin installation и места получения ресурсов также входят в миграцию.

Установка сначала проверяет manifest, версию контракта, режимы и обязательные файлы во временном пространстве, затем атомарно активирует версию. Ошибка не уничтожает предыдущую рабочую версию. Тест: установить RU и SL, обновить/удалить SL, убедиться, что RU и история сохранились. При конфликте обновления с сохранённым занятием старые ресурсы удерживаются либо предлагается явный перезапуск; не возобновлять новую очередь под старым идентификатором.

## 6. Занятие, история и прогресс

`activeSession` schema v2 хранит contentLanguage/contentVersion/packageId в нормализуемом context; восстановление сравнивает их наряду с учеником, темой, режимом, набором понятий и topicVersion. Несовпадение даёт объяснение и выбор перезапуска, без молчаливой подмены. Язык учебных элементов обозначается атрибутом `lang` даже при другом языке страницы.

Поля проходят весь путь: start → task generation → checkpoint → IndexedDB transaction + syncQueue → session.append → SQLite → serializers/bootstrap/history → восстановление. Проверить `shared/historical-session-statistics.mjs`, `session-statistics`, расчёт в `useConceptProgress` и клиентскую индексацию. Checkpoint и final одной сессии не меняют языковую идентичность.

Прогресс словаря разделяется по `(studentId, topicId, contentLanguage, conceptId)`; существующее общее использование понятия между режимами сохраняется до отдельного методического решения. Каждое обновление пакета не обнуляет прогресс: contentVersion хранится в истории, перенос между изменёнными concept IDs требует явного mapping. Общий отчёт по визуальным/математическим навыкам вводится отдельно после проверки сопоставимости.

Для legacy-истории нет надёжного общего правила «всё было ru»: импортированные материалы могли быть другими. Хранить неизвестный язык как null, а для технического ключа прогресса использовать зарезервированный `und` (не выбирать для нового занятия). Надёжно подтверждённые старые RU-материалы можно мигрировать по проверяемому правилу и журналу; неизвестное не зачисляется SL-прогрессом. Исходные записи сохраняются, миграция идемпотентна.

## 7. Озвучка и коммуникации

API речи принимает contentLanguage явно. Голоса фильтруются сначала по совместимому языку, затем по движку; «первый голос движка» перестаёт быть fallback другого языка. Отдельно обрабатывать поздний `voiceschanged`, отсутствие голоса, запрет autoplay, отмену и повтор. Словенский системный голос не считается гарантированным offline-ресурсом.

У каждого режима аудио классифицируется: необязательная помощь / существенная инструкция / основа задания. Для основы задания отсутствие утверждённого файла блокирует старт; для помощи показывается понятное взрослому состояние. Личные записи, названия букв и фонетические звуки имеют разные контракты; не заменять их общим TTS автоматически.

Сервисные ошибки постепенно получают `code` и параметры; клиент переводит code, сохраняя совместимость со старыми message на переходный период. Письма получают явный locale при создании события. В частности, письмо о покупке использует сохранённый язык согласия; изменение UI позже его не меняет. Существующие юридические версии сохраняются.
